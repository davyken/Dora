# Dora

Messaging that doesn't need a SIM card, mobile internet, or airtime credit.

Dora relays text, voice notes, and stickers between phones over Bluetooth to
nearby gateway nodes, which then hop the message across town over
long-range LoRa radio to a gateway near the recipient — no cellular tower,
no ISP, and no phone bill involved at any point. The full design rationale,
diagrams, and hardware bill of materials live in
[`docs/lora-mesh-architecture.pdf`](docs/lora-mesh-architecture.pdf) (and
just the diagram, on its own, in
[`docs/lora-mesh-diagram.pdf`](docs/lora-mesh-diagram.pdf)) — read that
first if you want the "why" behind the choices in this codebase.

This README documents the "what" and "how": what's actually implemented
today, what's intentionally stubbed pending real gateway hardware, and how
to build and run the app.

## Status: what's real vs. what's stubbed

Being upfront about this matters more than usual here, because half the
system (the gateway network) can't be finished without physical LoRa
hardware to test against. Nothing below is faked to look more complete
than it is.

| Capability | Status |
|---|---|
| On-device identity (Curve25519 keypair, no account/server) | ✅ Real |
| End-to-end encryption (NaCl box) | ✅ Real |
| Adding a contact — live QR scan | ✅ Real |
| Adding a contact — shared image / pasted link | ✅ Real |
| Contacts list, persisted locally | ✅ Real |
| Chat UI — text, voice notes, stickers | ✅ Real (recording, playback, local persistence) |
| Bluetooth **scanning** for nearby Dora devices | ✅ Real (`react-native-ble-plx`, central role) |
| Bluetooth **peripheral advertising** (so two phones can see each other with no gateway) | 🚧 Stub — needs a separate Android-only library and has real iOS OS restrictions; see `src/services/ble.ts` |
| Gateway hand-off protocol (phone → gateway over BLE) | 🚧 Stub — there is no gateway firmware yet to talk to |
| LoRa mesh relay (gateway → gateway) | 🚧 Not part of this repo — firmware for the ESP32/LoRa gateway boards is a separate project |
| Message delivery status beyond "queued" | 🚧 Depends on the gateway protocol above |
| Optional online contact directory / hybrid internet bridge | 🚧 Not started — see the PDF's "Optional Hybrid Bridge" section |
| Local notification when a message arrives | ✅ Real (`src/services/notifications.ts`), but nothing calls it yet — see below |
| Background listening (app closed, Android) | ✅ Real foreground service + persistent notification; toggle in Settings |
| Background listening (iOS) | 🚧 Not implemented — Apple's background-BLE restrictions make an always-on equivalent unreliable |

In short: **everything on the phone that doesn't require a gateway to
exist already works.** You can install this on two phones today, add each
other via QR code, and use the full chat UI — messages will sit at
"Queued" because there's no gateway to hand them to yet. That's the
correct, honest state of the system, not a bug.

## Tech stack

| Concern | Library | Why |
|---|---|---|
| App framework | React Native 0.87 (bare, not Expo) | Bluetooth peripheral/background needs outgrow Expo Go quickly |
| Navigation | `@react-navigation/native` + native-stack | Standard, well-supported |
| Identity & encryption | `tweetnacl` + `tweetnacl-util` | Small, audited, pure-JS Curve25519/NaCl — no native crypto module needed |
| Local storage | `@react-native-async-storage/async-storage` | Simple key-value store; swap for SQLite later if contact/message volume ever needs it (see comments in `src/services/storage.ts`) |
| Bluetooth | `react-native-ble-plx` | Most mature BLE **central**-role library for RN; peripheral/advertising is out of scope for it (see status table) |
| QR generation | `react-native-qrcode-svg` (+ `react-native-svg`) | Renders a contact's address as a scannable code |
| QR scanning | `react-native-camera-kit` | Built-in barcode/QR scanning without a separate frame-processor pipeline |
| Voice notes | `react-native-nitro-sound` | Actively maintained recorder/player (successor to the now-deprecated `react-native-audio-recorder-player`) |
| File system | `react-native-fs` | Where recorded voice notes are written before sending |

## How contacts work (no phone directory, no accounts)

There's no server anyone signs up to — a "contact" is just someone whose
public key you have. Three ways to get it, all implemented, all
zero-backend (`src/services/contactLink.ts`, `AddContactScreen.tsx`):

1. **Live QR scan** — open your profile QR, they scan it with their camera.
2. **Shared image or link** — screenshot your QR (or copy the `dora://add?p=…`
   link under it) and send it through any app you already have (WhatsApp,
   SMS, email). They scan the image from their gallery, or paste the link.
3. **Nearby list** *(scanning is real, resolving a device into a contact is
   not yet)* — an opt-in Bluetooth presence list of other Dora devices
   physically close to you right now.

Once added, a contact is permanent — messaging them later doesn't require
being nearby again, only that a gateway path exists between you (once
gateways exist).

## Notifications: local, not push — and why

There's no cloud server anywhere in Dora's design for a message to pass
through, so there's nothing for Firebase Cloud Messaging or Apple Push
Notification service to relay — the usual way apps get notified in the
background doesn't apply here. Instead, `src/services/notifications.ts`
implements **local** notifications: the phone notices, on-device, that a
message arrived over Bluetooth, and tells the OS to show a notification
itself.

That "noticing" has to happen somewhere even when the app is closed, which
is what the optional **background listening** toggle in Settings does on
Android: it starts a foreground service (the same mechanism music players
use) with a persistent, low-priority "Dora is listening" notification —
required by Android policy for any foreground service, not something this
app can hide. As of this version, the service has nothing real to listen
*for* yet (see the gateway hand-off stub above), but `messageService.receiveMessage()`
is already wired to decrypt an incoming payload, save it, and fire
`displayMessageNotification()` — so connecting the two is a one-line change
once gateway hardware exists, not a redesign.

iOS has no equivalent of an indefinite foreground service, and Apple
throttles background Bluetooth scanning hard enough that a reliable
always-on version of this isn't realistic there — the Settings toggle is
disabled on iOS for that reason rather than shipping something that quietly
doesn't work.

## Getting started

### Prerequisites
- Node.js ≥ 22.11 (see `engines` in `package.json`)
- For Android: JDK 21, Android Studio / SDK (compileSdk 37, NDK per
  `android/build.gradle`)
- For iOS: Xcode + CocoaPods (`cd ios && pod install`)

### Install
```bash
npm install
```

### Run
```bash
npm run android   # or
npm run ios
```

### Type-check & lint
```bash
npx tsc --noEmit
npm run lint
```

## CI: automatic APK builds

`.github/workflows/build-apk.yml` builds a debug APK on every push to
`main`, on any `v*.*.*` tag, and on demand (Actions tab → "Build APK" →
Run workflow). The output is always named after `package.json`'s
`version` field — e.g. version `0.0.1` produces `dora-v0.0.1.apk` — so
**bumping the version in `package.json` is what names the next build**.

- On a plain push to `main`: the APK is attached to the workflow run as a
  downloadable artifact (Actions tab → the run → Artifacts).
- On a `v*.*.*` tag push (e.g. `git tag v0.0.1 && git push origin v0.0.1`):
  the same APK is also attached to an auto-created GitHub Release.

This is a **debug** build — installable directly on a device for testing,
not something to publish to the Play Store as-is. To add a signed release
build later: generate a keystore, store it (base64-encoded) plus its
passwords as repository secrets, wire a `signingConfig` into
`android/app/build.gradle`, and swap `assembleDebug` for `assembleRelease`
in the workflow.

## Roadmap

Rough order, matching the priority of "what unblocks the most":

1. **Gateway firmware** (separate repo/project): ESP32 + LoRa boards
   running the BLE-peripheral + LoRa-mesh-relay protocol described in
   `docs/lora-mesh-architecture.pdf`. Nothing about phone-to-phone
   messaging becomes real until this exists.
2. **Gateway hand-off protocol** in `src/services/ble.ts`: once firmware
   exists to test against, replace `sendToNearestGateway`'s stub with a
   real BLE GATT write/read against it.
3. **Peer-to-peer BLE advertising** for the Nearby list to resolve into
   real contacts on Android (`react-native-ble-advertiser` or similar);
   document the iOS limitation rather than fighting it.
4. **Voice note chunking** for LoRa's small packet size (see the TODO in
   `messageService.ts`).
5. **Optional hybrid internet bridge + directory service** (thin NestJS
   backend) — lets two people who've never met find each other when at
   least one has occasional internet access.
